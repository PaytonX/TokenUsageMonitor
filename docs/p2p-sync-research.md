# 多端同步：P2P + 鉴权替代 hub 的方案调研

> 结论先行：**建议不引入 libp2p，改用「mDNS 发现 + 局域网直连 + 配对鉴权」的轻量方案，且与现有 hub 并存而非替换。**
>
> 调研日期：2026-09-28　对应想法：想法池 #3　代码基线：`feat/logo-pill-edge-peek` @ `3b1c468`

---

## 一、先看清现状：现有 hub 到底在做什么

在讨论替代之前，必须先明确 hub 的实际形态——这决定了 P2P 方案要解决的是哪个问题。

### 1.1 数据模型与规模

`src-tauri/src/hub.rs` 的 `HubDevice`（L24-40）每台设备上报：

| 字段 | 类型 | 量级 |
|---|---|---|
| `device_id` / `hostname` / `os` / `arch` / `version` | 字符串 | 数十字节 |
| `tool_tokens` / `provider_count` / `tool_count` | 数值 | 数十字节 |
| `daily` | `Vec<HubDay>` | **90 项上限**（`tool_daily_from_cache` L277-279 强制裁剪） |

**关键结论：单条上报约 90 个 `{date, total}` 对象，量级在 10 KB 以内。** 这是个非常小的负载——远达不到需要 P2P 分片、流控或分片的门槛。

### 1.2 拓扑：角色互斥（这是最关键的事实）

`src-tauri/src/lib.rs` L352-391 的装配逻辑：

```rust
if start.hub_mode == "hub"    { hub::spawn_hub_server(...); }   // 只监听，不上报
if start.hub_mode == "agent" && start.report_on { /* 30s 循环上报 */ }
```

`hub_mode` 是**字符串单值**（`off` / `hub` / `agent`），一个实例**只能二选一**。这意味着：

> 现有架构里，hub 节点**看不到自己**的用量；只有 agent 节点的数据会被汇总。

这个设计对 P2P 改造有决定性影响：**P2P 要求每个节点既是服务提供方又是消费者**，与现有的互斥角色直接冲突。无论选哪种方案，角色模型都必须先调整为「每个实例都监听 + 都上报」。

### 1.3 协议与鉴权现状

- 手写 HTTP/1.1（`TcpListener` + `BufReader`），仅两个端点：`POST /ingest`、`GET /devices`
- 鉴权：可选 Bearer token，`token` 为空则**全部放行**（L160-165）
- 无 TLS（局域网明文 HTTP）
- 持久化：SQLite

## 二、候选方案评估

### 方案 A：libp2p

**成熟度**：高。官方文档将 `rust-libp2p` 列为 Production-Ready 实现，v0.56（2025-06）起持续维护，另有 Parity 的 `litep2p`（v0.13.3，2026-03）作为轻量替代。生态支撑 IPFS / Ethereum 2 / Filecoin / Polkadot。提供 Noise / TLS 1.3 安全通道、mDNS & Kademlia DHT 发现、DCUtR 打洞、Circuit Relay v2 中继。

**但对本项目而言是过度设计**，理由：

| 维度 | 本项目实际需要 | libp2p 提供 |
|---|---|---|
| 传输 | 局域网 HTTP 直连 | TCP/QUIC/WebSocket/WebRTC/Bluetooth/… |
| 节点发现 | 同网段广播 | mDNS + Kademlia DHT + relay |
| 节点规模 | 2~5 台个人设备 | 跨互联网去中心化 |
| 冲突处理 | 无（单写者，hub 覆盖） | gossipsub 等复杂协议 |
| 依赖成本 | 现有取向是「不引入额外依赖」 | 数百个传递依赖 |

**P2P 的核心价值是「跨 NAT 网络下的去中心化与抗审查」**，而本项目是个人自用的局域网用量汇总——这个价值在这里不存在。

**参考案例的启示**：NexDesk（Tauri + webrtc-rs，真正的 P2P 远程桌面）**仍然需要信令服务器**来交换连接信息。P2P 极少能真正消除中心节点，只是把中心节点的作用缩小到"牵线"。

### 方案 B：mDNS 发现 + 局域网直连 + 配对鉴权 ✅ **推荐**

**成熟度**：高且轻量。
- `mdns-sd`：纯 Rust 实现，8.9K SLoC，27.7 万次下载，83 个版本，**无异步运行时依赖**，支持 Windows/macOS/Linux + IPv4/IPv6
- `mdns-sd-discovery`：走系统原生栈（Windows 10+ 的 Win32 DNS-SD API），Tokio 异步
- `zeroconf`：跨平台封装，v0.18.0（2026-04）

**工作方式**：
1. 每个实例在局域网广播一个 mDNS 服务（如 `_tokenusage._tcp.local`），TXT 记录携带设备 ID 与公钥指纹
2. 互相发现后直连 HTTP，**沿用现有的 `HubDevice` 数据模型与两个端点**
3. 首次配对时，用户在一台设备上确认显示的短码（或扫描二维码），建立信任关系
4. 之后用 Ed25519 签名 + 噪声握手（或简单的共享密钥）鉴权

**为什么这个方案最合适**：
- **完全复用现有代码**：`HubDevice`、`/ingest`、`/devices` 语义不变，只是把"知道 hub 地址"换成"mDNS 自动发现"
- **依赖增量极小**：`mdns-sd` 自身无运行时依赖，不破坏项目的轻量取向
- **真正去中心化**：无中心节点，每台机器都能汇总全网数据（需解决 §1.2 的角色互斥问题）
- **保留 hub 作为可选**：跨网段场景（如公司 vs 家里）仍可用 hub

**必须正视的三个坑**：
1. **Windows 防火墙**：入站连接会被拦截，首次需引导用户添加入站规则。这是 mDNS 方案最大的落地摩擦。
2. **mDNS 仅限同网段**：跨网段无能为力，此时仍需 hub 或 Tailscale。
3. **多网卡/容器网络**：mDNS 组播在 Docker bridge、部分 VPN 环境下不可达。

### 方案 C：Tailscale / 组网方案

Tailscale 基于 WireGuard，天然提供设备发现、加密与跨网段穿透，用户体验最佳。

**但**：引入外部服务依赖（协调服务器）、需用户安装第二个软件、且与"本地优先无账号"的取向冲突。适合作为**文档中提及的可选路径**（"跨网段时可配合 Tailscale 使用"），不适合作为默认方案。

### 方案 D：CRDT（Automerge / yrs）合并

调研发现两个成熟的 Rust CRDT：
- **Automerge 2.0**：Rust 重写，官方称 production-ready，维护团队含 Heroku 联合创始人、剑桥教授 Martin Klemmann，有 Ink & Switch 全职工程团队支撑
- **yrs 0.28**：Yjs 的 Rust 移植，Y.Map / Y.Array / Y.Text 共享类型 + 二进制 state-vector 差量同步；有产品从 Automerge 迁移到 yrs 后报告**编辑快 47×、合并快 40×、同步载荷小 6×**

**但本项目目前不需要 CRDT**：数据是**单写者的汇总**（每台设备只写自己的用量，全网汇总是并集操作），**不存在并发写冲突**。CRDT 解决的是"多端并发编辑同一文档"，而这里天然没有这个问题。

仅当未来出现"多端同时修改同一份配置"的需求时才值得引入。

## 三、方案对比总表

| 维度 | libp2p | mDNS+直连+配对 | Tailscale | CRDT | 现状 hub |
|---|---|---|---|---|---|
| 去中心化 | ✅ | ✅（限同网段） | ⚠️ 依赖协调服务器 | — | ❌ |
| 依赖增量 | 数百个传递依赖 | 1 个轻量 crate | 外部软件 | 中等 | 0（手写） |
| 复用现有代码 | ❌ 需重写协议层 | ✅ 数据模型不变 | ✅ | ❌ | — |
| 跨网段 | ✅ | ❌ | ✅ | — | ✅ |
| 鉴权成熟度 | ✅ 内置 | 需自建配对 | ✅ | — | ⚠️ 明文 HTTP |
| 落地摩擦 | 高 | 中（防火墙） | 中（装软件） | 高 | 低 |
| **本项目适配度** | ❌ 过度设计 | ✅ **最合适** | ⚠️ 备选 | ❌ 无冲突可解 | 现状 |

## 四、推荐路径

### 阶段 0：先做无风险的改进（不引入任何依赖）—— ✅ 已实施（`0013a10`）

无论最终是否上 P2P，这两项都值得做，且**能解决当前架构的实际缺陷**：

1. **让 hub 节点也能上报自己** ✅
   现状 hub 节点看不到自身用量（§1.2）。已实施：hub 模式启动后按 **30s 周期**把本机用量 upsert 进 `hub_devices` 表（`build_self_device` 与 agent 共用同一构造函数，保证两角色数据口径一致）。

   > 实施中踩到的坑：第一版只在启动 6s 后写一次，实测 `tool_tokens` 恒为 0——本地工具扫描需要预热，写一次就永远留下空快照。改为 30s 周期刷新后才拿到真实值（实测 1451853475.0 / 5 tools / 90 天 daily）。**周期刷新是必需的，不是优化。**

2. **把 Bearer 鉴权改为默认必填** ✅
   现状 `token` 为空则完全放行（§1.3）。已实施：启用 hub 时若**尚未配置**密钥，自动生成 32 位十六进制（128 bit `getrandom`）并落盘。

   > **关键设计**：用新增的 `hub_token_configured` 区分「从未设置」与「显式清空」。老配置无此字段 → `serde(default) false` → 视为未设置从而补发密钥；用户若主动清空（有意关闭鉴权）→ 前端保存时置 `true` → 之后不再被填回。没有这个区分，「默认安全」就会变成「无法关闭鉴权」。

> **副作用提醒**：存量用户首次以 hub 模式启动后 `hub_token` 会被自动写入，**agent 端需同步填写同一密钥**，否则上报将被 401 拒绝（预期行为，但升级时需告知用户）。另外设备页现在会出现汇总节点自己这一行。

### 阶段 1：mDNS 发现 —— ✅ 已实施（`3b3d0a3`，`hub_mode = "lan"`）

保留现有 hub 端点与数据模型，新增发现层：

- 新增 `src-tauri/src/p2p.rs`：`mdns-sd` 广播 `_tokenusage._tcp.local`，TXT 携带 `device_id`
- 角色：新增 `lan` 模式 —— 复用 hub 的监听 + 密钥生成 + 本机自写入，额外增加"向每个已发现对端上报"，形成**全连接 mesh**
- 鉴权：复用现有共享密钥（`hub_token`），`lan` 模式同样在缺省时自动生成
- 跨网段：**不变**，仍由 `hub_mode = "agent"` + 手动 `hub_base` 承担（用户明确要求两者并存）

**用户决策（2026-09-28）**：

| 决策点 | 选择 |
|---|---|
| 跨网段如何覆盖 | hub 保留承担跨网段，mDNS 只管同网段 |
| 同网段拓扑 | 全连接 mesh：每台既监听又上报 |
| 配对鉴权 | 复用现有共享密钥（不做每机密钥对） |
| 节点规模 | 10 台以内 |

**关键推论**：规模 ≤10 台且全连接 ⇒ 每台直接上报给其余 9 台，**一跳即全知**。因此不需要 Gossip/多跳转发（会引入重复计数与环路风险），`hub_device` 表以 `device_id` 为主键的设计天然适配。

**实现要点**：
- 对端以 `device_id` 去重（**而非地址**），否则 DHCP 续租后设备页会出现重复行
- 跳过回环与 `0.0.0.0`，否则本机会向自己上报形成自我循环；过滤 `device_id` 等于自己的回环发现
- 多网卡时对端地址排序选取，保证行为可复现（`HashSet` 无序）
- 启动失败或网络禁 multicast 时 `peers()` 恒为空，**静默降级**为手动 hub

**依赖**：`mdns-sd` 0.21.4（纯 Rust、无 C 依赖），连带 `flume` / `if-addrs` / `socket-pktinfo` / `spin`。

**实测（2026-09-28，真实 config.toml 切到 lan）**：监听 43210 成功；模拟对端上报返回 200；设备汇总正确列出 3 台（含 daily 90 项）；错误 token 返回 401。新增 8 个 p2p 单测；`cargo test` 142 passed。

> **⚠️ 未验证项**：真实双机 mDNS 互发现。Tauri 单实例插件不允许同机双开，且 `device_id` 取自 `hostname`，同机两实例会被回环过滤。需用户在两台真实机器上实测（含 Windows 防火墙放行）。

## 五、需要用户决策的点

1. **是否接受 Windows 防火墙提示**：mDNS 直连需要用户添加入站规则，这是最大的落地摩擦。是否可接受，或需要提供开关（默认关闭 P2P，仅局域网手动填 IP）？
2. **是否需要跨网段**：如果需求主要是"家里 + 公司两台机器"，mDNS 不够，需引入 Tailscale 或保留 hub 作为跨网段通道。
3. **节点规模预期**：2~5 台（个人自用）还是更多？若规模小，简单的手动填 IP + 共享密钥可能比 mDNS 更省事。
4. **是否接受"与 hub 并存"**：本方案的推荐是不替换 hub，而是让 P2P 成为同网段的便捷路径。若期望彻底移除 hub，需重新评估。

## 六、结论与建议

**推荐**：走「阶段 0 → 阶段 1」，即先修 hub 节点看不到自己的问题 + 强制 token，再叠加 mDNS 自动发现，**与 hub 并存**。

**不推荐** libp2p：本项目是局域网个人自用场景，P2P 的核心价值（跨 NAT 去中心化、抗审查）在此不成立，引入数百个依赖与项目"轻量、不引入额外依赖"的取向直接冲突。

**不推荐** CRDT：当前数据是单写者汇总，无并发冲突可解。

**核心洞察**：P2P 不等于"没有中心节点"。即便是成熟的 P2P 产品（如 NexDesk）也依赖信令服务器。对本项目而言，真正的收益不是"去中心化"，而是**免去手动填写 hub 地址**——用 mDNS 达成这个收益，成本远低于 libp2p。
